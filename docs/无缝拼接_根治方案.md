# 无缝连贯拼接 · 根治方案（诊断 + 两套解法 + MiniMax H3 评估）

> 日期：2026-08-12（初版） / 2026-08-20（两轮根治：transition_video → 原生调度，见 §零）
> 结论一句话：**"拼接"模式看着像转场，根因不在拼接而在"生成"——多段各自独立去噪后用混合盖接缝，永远只能掩盖；真无缝必须让相邻段在生成阶段就共享同一条去噪轨迹。**
> 2026-08-20 追记（最终态）：多段无缝(A) 的**根治主路径已切换为原生调度式长视频**（`SCAIL2ScheduledLongVideoWithSAM` 节点内 `previous_frames` 尾帧锚定 + 张量层一次成片，**根本不存在文件拼接环节**）；`transition_video` 硬冻结代码保留、仅显式 WanAnimatePlus 家族路线生效；拼接淡化彻底降级为安全网。

## 零、2026-08-20 根治落地（两轮迭代后的最终态）

### 0.1 根因

用户实测：`多段拼接依然不自然连贯——前一段的尾帧并不是下一段的首帧，导致视觉断层。`

无论 `transition_video`（肥猴 SQR，外部分段架构）还是原生调度（FaboroHacks，节点内部分段），本质都是**生成侧硬锚定**：把上段尾帧作为下段去噪的硬约束。事后混合（淡化/latent 混合/交叉溶解）只能掩盖，4 步蒸馏下掩盖不住。

### 0.2 两套参考工作流的事实定位（节点清单核对）

| 参考目录 | 核心节点 | 多段机制 | 对本项目的价值 |
|---|---|---|---|
| `三层楼的小肥猴/【分段队列】系列` | `SegmentQueueRunner` + `WanAnimatePlus SCAIL_2 Embeds.transition_video` | 外部分段队列：上段成片尾 21 帧注入 `transition_video` → 画布头冻结硬续写 → Decode 自动裁掉 | 外部分段架构（与本引擎同构）的根治参考 |
| `FaboroHacks/两个 Face Detailer` | `SCAIL2SegmentPlanBuilder` + `SCAIL2ScheduledLongVideoWithSAM` | **节点内部调度**：`previous_frames[-overlap:]` 尾帧锚定（去噪层硬约束）→ `discard_head` 去重 → `torch.cat` 张量层一次成片 | **接缝终极根治**：压根没有"分段成片文件再拼接"环节 |

### 0.3 第一轮：transition_video 尾帧硬冻结（已落地，后经实测回退为条件生效）

机制（对 ComfyUI-WanAnimatePlus/nodes.py 实测）：
- Embeds 检测到 `transition_video` → `canvas_expansion_px=21`，`num_frames` 自动 +21；
- 画布头 21 帧冻结为上段成片尾帧（`freeze_frame_mask=1`，姿态条件置零）→ 采样硬约束从上段尾帧续演化；
- Decode 自动 `images[:, canvas_expansion_px:]` 裁掉扩充值 → 无重复帧。

**实测教训（d77bd30 回滚原因）**：把多段无缝默认模板切到内置 Tier2(WanAnimatePlus) 后，本机画质崩坏（无动作迁移/画面粗糙）且输出到 `yunjii_tier2` 造成双文件夹。结论：内置 Tier2 模板不可作为多段默认。已回滚：
- 多段无缝默认模板恢复标准官方 SCAIL 子流程；
- planner 重叠恢复 3efa21f 基线（多段无缝=UI 值 8，智能分段锁 32）；
- `_inject_transition_video` 代码**保留**：仅当用户显式提供 WanAnimatePlus 家族模板/暖启动路线时生效。

### 0.4 第二轮（最终态）：多段无缝(A) 自动切原生调度式长视频

**现行主路径**（`engine/runner.py`）：`SCAIL-2 路线` + `多段无缝(A)` + 已安装 `comfyui_scail2_multi_cond` → 自动切 `_run_native_scail2`（FaboroHacks 同款）：

- `previous_frames` 尾帧锚定：每块生成长度=keep+overlap，头部 overlap 帧被上块尾帧**在去噪层面硬约束**（源码 nodes.py:2696 `previous_frames[-actual_overlap:]`）；
- `discard_head` 丢弃锚定头（nodes.py:2740）→ 无重复帧；
- 重叠区颜色校正 `_match_chunk_color_like_original`（nodes.py:1236）→ 消除段间色差漂移；
- `torch.cat(frames, dim=0)` 张量层一次成片（nodes.py:833）→ **无文件拼接环节，接缝物理上不存在**；
- 实参对齐 FaboroHacks 验证值：`max_chunk_frames=81 / overlap_frames=5`；本机已实跑验证（2026-08-15，49 帧成片成功）。

未装原生包则回退既有模板分段路线并告警（接缝退化为拼接侧帧锚定淡化，非根治）。

### 0.5 现行连续性层级（自上而下回退）

1. **原生调度式长视频**（多段无缝 A 默认，FaboroHacks 同款）——去噪层硬锚定 + 张量层成片，无拼接环节；
2. **transition_video 尾帧硬冻结**（肥猴 SQR 同款）——仅显式 WanAnimatePlus 家族模板/暖启动路线，像素级硬保证；
3. 上段落盘 latent 续写（reference_latent / samples+noise，原「真骨架」路径）；
4. `prefix_frames` 像素冻结（旧 Tier2 行为，弱锚定）；
5. 拼接阶段帧锚定淡化（安全网：失配 <0.02 → B=0 纯顺序拼接；失配大才自适应淡化兜底）。

### 0.6 冒烟验证（`_smoke_transition.py`，python_embeded 实跑，21/21 通过）

- T1 planner：200帧→3段[81/81/53]，每段≤81、多段无缝重叠=UI值8、智能分段锁32、边界按重叠交叠 ✅

## 一、为什么现在的"真·一镜到底潜空间拼接"其实是转场

### 1.1 你看到的三件套为何雷同

| 你试的模式 | 代码值 | 它在做什么 | 观感 |
|---|---|---|---|
| 转场·交叉淡化 | `STITCH_CROSS_DISSOLVE` | ffmpeg xfade 真交叉溶解 | 明显转场 |
| 一镜到底（重叠混合） | `STITCH_SEAMLESS_BLEND` | 接缝处 8 帧像素交叉溶解 | 软化但仍像过渡 |
| 真·一镜到底（潜空间） | `STITCH_LATENT_BLEND` | 段 latent 接缝处 latent 交叉淡化后重解码 | **本质是 latent 层面的淡入淡出，仍是转场** |

三者都是"**事后在两端做混合**"，区别只在混合发生在像素还是 latent、混合窗几帧。所以你感觉"都一样"——因为它们确实是同一类东西。

而 `STITCH_SEAMLESS`（**硬切 + 丢弃后续段头部重叠帧**）是真正"无效果"的硬接，但它只在**生成本身就连续**时才会"看不出是两段"；否则硬切反而把跳变暴露得更明显。这正是你之前没选它、或选了也觉得不对的原因——生成端没连续，硬切也救不了。

### 1.2 生成端真正的断点（代码铁证）

核对 `workflows/SCAIL2_embed子流程_官方_20260728_0230.json` 与本机适配器：

1. **`WanVideoContextOptions` 根本没有接进采样器。**
   - 模板里 `WanVideoContextOptions`(id=355) 存在，`reference_latent → None`。
   - 但它的下游 `WanVideoSamplerv2`(id=348) 的 inputs **没有 `context_options` 链接**。
   - 这意味着 WanVideo 的"上下文滑动窗口"（uniform_standard / context_frames=81 / context_stride=4 / context_overlap）**完全没生效**——每段是孤立去噪。
2. **模板 `context_overlap=48` 且未接线**，毫无意义（记忆里"锁 32"指的是段间 STITCH 重叠，不是这个 context_overlap）。
3. **我们的"根治"只是弱锚定**：`_inject_latent_warmstart` 把上段成片编码成 latent 喂 `sampler.samples` + `add_noise_to_samples=True` 重新去噪。4 步蒸馏下加噪几乎抹掉锚点 → 段边界仍跳 → 只能靠 stitcher 混合盖住。这就是"转场感"的来源。
4. **标准 SCAIL 适配器的 `SCAILNodeMap` 连 `context_options` 字段都没有**（只有 sampler/decode/combine），所以适配器从未碰过滑窗节点。AnimatePlus 适配器虽有 `context_options`，但从未把上段 latent 喂进 `reference_latent`。

### 1.3 猴子工作流为什么丝滑（真机配方）

解析 `三层楼的小肥猴` 文件夹中最新分段队列工作流，确认无缝真因：

- `WanVideoContextOptions` / `WanAnimatePlus ContextOptions` 配置：
  `context_schedule=uniform_standard, context_frames=81, context_stride=4, context_overlap=32`（即 8 latent 帧）。
  且 **`SamplerSettings`/`Samplerv2` 的 `context_options` 输入是接上的**（同一次采样内滑窗）。
- `SegmentQueueRunner` 负责把**上一段的尾帧/潜空间作为下一段的 `reference_latent` 续写**。
- 核心区别：**整条长视频是同一条去噪轨迹**，重叠的 8 latent 帧是作为"条件上下文"喂给同一次采样，不是事后混合。接缝天生不存在，硬切即可。

## 一·五、方案 A / B / C —— 用户可选的统一入口（互不冲突）

> **核心结论：A 与 B 并不冲突，而是同一套真·无缝机制的两种目标档位，两者都做、由用户按视频时长选择。** C 是旧单遍方案的兜底/对比位。三者已在代码里落地为 `engine/types.py` 的 `SEAMLESS_PLAN_A/B/C` 与 Planner/Runner 的「无缝连贯方案」下拉。

### A/B/C 共用同一套真·无缝机制

三者都依赖：把 `WanVideoContextOptions` 滑窗接进采样器（`context_overlap=32=8 latent 帧`）+ 跨段 `reference_latent` 续写（上段 latent 喂下一段上下文窗口，使多段同一条去噪轨迹连续）+ 拼接用 `STITCH_SEAMLESS` 零转场硬切。区别只在**目标时长靶心与长程防漂移增强**：

| 档位 | 适用场景 | 生成机制 | 优点 | 缺点 / 代价 | 与谁冲突 |
|---|---|---|---|---|---|
| **A 方案**·标准多段无缝（默认） | 一般时长 ≤15s 的多段连续 | 每段独立高保真生成 + context 续写；`long_video_mode=False` | 每段质量最高、显存友好、可单段独立重试、耗时最短 | 超长视频(>15~20s) 段数多，长程姿态/光影漂移会累积 | 无（与 B 互补） |
| **B 方案**·超长视频无缝 | 15~30s+ 长视频无断点 | 同样是 context 续写，但 `long_video_mode=True`：强制 SCAIL 真骨架(逐帧姿态)防漂移 + 加大重叠冗余 + 按容量自动分块(81帧×N段，9段≈30s+) | 长视频无断点、无质量降级，最适合"一镜到底长片"；与 MiniMax H3 分段参考延长同源但**兼容本机 SCAIL-2** | 段数多 → 总耗时线性增加；某段失败需重跑该段(已有机制) | 无（与 A 互补） |
| **C 方案**·单遍连贯（旧方案C） | 兜底 / 理论最连贯对比 | 整片一次去噪（latent 天然连续） | 零分段、一次去噪理论最连贯 | 长视频被长程重度混合稀释→画质软、显存峰值高、不可分段重试 | 不推荐主用，仅备选 |

### 用户怎么选（UI 位置）

- **「分段规划器」节点**新增下拉 **「无缝连贯方案」**：`A方案(默认) / B方案(超长) / C方案(单遍兜底)`。选它即覆盖旧的「连贯策略」语义，成为无缝档位主入口。
- **「完美模仿(执行)」节点** 同步接收该字段（写回 `plan.seamless_plan`），即使规划器未跑、直接用旧 plan 也能生效。
- **拼接模式务必选 `无缝一镜到底(零转场·硬切) ⭐推荐`**（`STITCH_SEAMLESS`），而**不要选**标注 `[转场]` 的 `潜空间拼接/重叠混合/交叉淡化`——后者本质都是事后混合，正是你之前嫌的"像转场"。

### 一句话决策

> 短视频（≤15s）→ 选 **A**；长视频（≥15~30s）怕漂移 → 选 **B**；想试一次去噪的极端连贯（不计画质代价）→ 选 **C**。A 与 B 是主推互补路线，建议都保留给用户按需切换。

## 二、方案 A：完全无感连贯拼接多段视频（生成端根治，= 无缝连贯方案 A）

### 2.1 机制（对齐猴子，已在代码中实施脚手架）

1. **启用滑窗**：把 `WanVideoContextOptions` / `WanAnimatePlus ContextOptions` 接进采样器（`sampler.context_options = [context_options_id, 0]`），`context_overlap` 锁 32（8 latent 帧）。→ 单段内本身更连贯。
2. **跨段连续续写**：对 `seg>0`，把**上一段落盘的尾部 latent**（`seg_{i-1}_latent.pt`）加载后喂进 `context_options.reference_latent`。→ 下一段头部 = 上一段尾部（同一条去噪轨迹），边界消失。
3. **拼接改硬切**：生成连续后，拼接模式用 `STITCH_SEAMLESS`（硬切 + 丢重叠头帧，零混合）。这才是你要的"无效果、看不出拼接"。
4. **安全回退**：`reference_latent` 注入为 best-effort（`try/except`）；若失败自动回退到现有 `latent_warmstart`（samples+add_noise 弱锚定），**绝不比现在更差**。

### 2.2 代码改动清单（已落地，待 GPU 验证）

- `engine/adapters/scail.py`
  - `SCAILNodeMap` 新增 `self.context_options = ""`；`discover_nodes` 识别 `WanVideoContextOptions`。
  - `modify_workflow_for_segment`：① 接 `sampler.context_options`；② `context_overlap` 置 32；③ `seg>0` 时 best-effort 注入 `reference_latent`（加载上段 latent → 喂 context_options），失败回退现有 `_inject_latent_warmstart`。
- `engine/adapters/animateplus.py`
  - 已有 `context_options`；`seg>0` 时把上段 latent 喂进 `WanAnimatePlus ContextOptions.reference_latent`（取代/补充弱 samples 锚定）；Tier2 仍保留像素 prefix 冻结。
- `engine/stitcher.py`
  - `STITCH_SEAMLESS`（硬切 + 丢重叠头帧）即"无效果硬接"，作为真·一镜到底默认拼接；`STITCH_LATENT_BLEND` 退为可选（它本质是 latent 转场，不应再是默认）。

### 2.3 验证清单（本机 RTX 3090 实跑）

日志应出现：
1. `SCAILAdapter … 采样器接入 context_options(滑窗, overlap=32)`
2. `SCAILAdapter … 跨段 reference_latent 续写: prev=seg_{i-1}_latent.pt → context_options.reference_latent`（或 AnimatePlus 同名日志）
3. 拼接日志 `📊 真·一镜到底（硬切连续）` 而非 `接缝混合 N 帧`
4. 目测：段边界无跳变、无淡化，硬切处看不出接缝。

**拼接模式选择**：生成连续后，请选 `STITCH_SEAMLESS`（真·一镜到底·硬切连续 / 丢重叠头帧、零混合）——这才是你要的"无效果硬接"。**不要再选 `STITCH_LATENT_BLEND`（潜空间拼接）**，它本质是 latent 层面的淡入淡出转场，正是你之前觉得"和转场一样"的来源。

**一键回退开关**：若本机 GPU 执行时某段因 `reference_latent` 报错（极少概率，属 latent 格式兼容问题），设置环境变量 `YUNJII_DISABLE_REF_LATENT=1` 后重跑，即自动退回旧的 `samples+add_noise` 弱锚定（等价改前行为），无需改代码。验证根治生效后可移除该变量。

若 ② 缺失：说明模板无 `context_options` 节点或上段 latent 未落盘，已自动回退旧路径（见 §四）。

## 三、方案 B：15s 以上（目标 30s+）长视频不劣化（= 无缝连贯方案 B · 长程防漂移）

> 用户在「分段规划器」选 **B 方案·超长视频无缝** 即启用本节机制（`long_video_mode=True`）。

### 3.1 同一机制即可支撑长视频

context_options 链式续写天然支持超长：把 30s（@24fps≈720 帧）切成 ~9 段 ×81 帧，靠 `reference_latent` 一直接下去。关键风险是**长程漂移**（人物/背景随时间 morph、内容走形）。

### 3.2 防漂移靠 SCAIL 真骨架

我们的 SCAIL-2 是**姿态/结构驱动**（pose embeds），每一段内容由骨架序列决定，而非自由生成 → 身份/背景/构图被结构强锚定，**漂移被天然抑制**。这正是选 SCAIL-2 路线而非纯 Wan 自由生成的理由。配合：
- 适当加大 `context_frames`（≤81，Wan 上下文窗口上限）让每段内部更稳；
- 保持 `reference_latent` 跨段续写（段间不断轨）；
- 可选 `CONTINUITY_SINGLE_PASS`（方案C 单遍）做"单次超长去噪"，但 4 步蒸馏下长程会被稀释画质下降，仅适合对画质不敏感场景。

### 3.3 结论

- **30s+ 无劣化的主路径 = 方案 A 的 context_options 链式续写 + SCAIL 真骨架防漂移 + 多段拼接**（每段 81 帧质量满血，不牺牲单段画质）。
- 单遍(方案C)仅作"真·一次去噪"的备选，画质有代价。

## 四、MiniMax H3 评估（是否值得作为考虑）

### 4.1 事实（2026-08-11 联网核对）

- 发布：2026-07-31 / 08-02；2026-08-03 开源权重（社区协议，EU/UK/US/KR 需授权）。
- 能力：**单条最长 15 秒封顶**（2K / 768p，24fps，原生立体声）。定价 0.8 元/秒(2K)。
- 长视频：Ref2VA 变体支持 "**把已生成视频作为参考输入、顺序延长**" 的长视频方法——但这仍是"15s 一段、逐段参考延长"，**不是一次性 30s**；且延长处的连续性依赖其 In-context Regeneration，与我们要做的"参考续写"是同一原理。
- 本地部署：RTX 4090 上 15s@1248×832 ≈20 分钟；需独立 ComfyUI 节点（H3 非 Wan/SCAIL 架构）。
- 亮点：原生音视频同出、Omni Reference（多图/视频/音频参考）、指令遵循强。

### 4.2 对本项目的判断

| 维度 | 结论 |
|---|---|
