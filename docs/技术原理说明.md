# 云集智能 V2V 引擎 — 技术原理说明

## 一、整体架构概览

云集智能 V2V（Video-to-Video）引擎是一个 ComfyUI 自定义节点插件，核心目标是：**输入一段参考视频，自动分析其内容，然后利用 WanVideo 模型重新生成一段风格/内容可控的新视频**。

整个系统分为 **分析层** 和 **引擎层** 两大部分：

```
┌─────────────────────────────────────────────────────────────────┐
│                        ComfyUI 工作流                            │
│                                                                 │
│  ┌─── 分析层（5个节点）──────────────────────────────────────┐   │
│  │                                                           │   │
│  │  运动分析 ──→ 提示词控制 ──→ 关键帧预览                   │   │
│  │     │          │                                          │   │
│  │     │     姿态提取    模仿提示词                           │   │
│  │     │                                          │          │   │
│  └─────┼──────────────────────────────────────────┼──────────┘   │
│        │                                          │              │
│  ┌─── 引擎层（3个节点）──────────────────────────────────────┐   │
│  │                                                           │   │
│  │  分段规划 ──→ 链式执行 ──→ 无缝拼接                       │   │
│  │                                                           │   │
│  └───────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 数据流全貌

```
参考视频 (.mp4)
    │
    ▼
┌──────────────────┐
│  运动分析 🔍      │──→ 运动提示词 (STRING, "|||"分隔)

    ▼               ▼

│ 姿态提取 🕺   │  │ 模仿提示词 🎭   │

│              │  │                │

                   │              │

                   └──────────────┘
                          │
    分段信息               │ 分段提示词
    ──────────────────────┼────────────────────
                           ▼
                   ┌──────────────┐
                   │ 分段规划 🧠   │
                   │ Planner      │
                   │              │
                   │ → 段落计划   │ (JSON)

                   段落计划 + 工作流模板

                          ▼

                   │ 链式执行 ⛓   │  ←── 通过 HTTP API 提交子任务

                   │              │

```

## 二、分析层节点详解

### 2.1 运动分析 🔍 (MotionAnalysisNode)

**源码位置**: `nodes.py` → `MotionAnalysisNode`

**功能**: 输入一段视频，自动完成镜头检测、人物检测、运动分析，输出分段信息和提示词。

#### 执行流程

```
输入视频
  │
  ├─ 1. 打开视频 (cv2.VideoCapture)
  │     → 获取总帧数、FPS、时长
  │
  ├─ 2. 镜头边界检测 (_detect_scene_boundaries)
  │     → HSV直方图对比法：计算相邻帧的HSV直方图相关度
  │     → 相关系数 < 阈值(1.0 - 灵敏度*0.5) → 认为是镜头切换
  │     → 采样步长=2，每2帧检测一次（加速）
  │
  ├─ 3. 分段模式选择
  │     ├─ 自然镜头: 按检测到的边界分段，合并过短段(<最小秒数)，拆分过长段(>最大秒数)
  │     ├─ 均匀时长: 按最大秒数均分，优先在镜头边界处切割
  │     └─ 固定段数: 指定段数均分，优先在镜头边界处切割
  │
  ├─ 4. 人物检测 (_detect_person_in_scenes)
  │     → 对每个镜头取1/4、1/2、3/4位置帧
  │     → Canny边缘检测 + 下半部分边缘密度分析
  │     → 下半边缘密度>5% 且 全局密度>4% → 判定为有人物
  │     → 注意：这是轻量级启发式检测，非深度学习模型
  │
  ├─ 5. 运动分析 (_analyze_motion)
  │     → 对每个镜头取4个检查点帧
  │     → Farneback光流法：计算帧间像素运动向量
  │     → 水平运动>1.5px → "camera panning left/right"
  │     → 垂直运动>1.5px → "camera tilting up/down"
  │     → 帧间差异>50%像素 → "major scene change"
  │
  ├─ 6. 关键帧提取
  │     → 每个镜头取中间帧（可加帧偏移微调）
  │     → 合并手动选帧
  │     → 保存为PNG到 output/keyframes_视频名/
  │
  └─ 7. 输出
        → 运动提示词: "|||"分隔的每段运动描述
        → 分段信息: 含帧号格式 "帧0-96 (0.0s-3.2s, 3.2秒)"
        → 视频路径: 完整绝对路径，供下游姿态提取使用
```

#### 关键技术细节

| 技术 | 实现 | 说明 |
|------|------|------|
| 镜头检测 | HSV直方图相关度 | `cv2.calcHist` + `cv2.compareHist(HISTCMP_CORREL)` |
| 人物检测 | Canny边缘密度 | 下半身边缘密度启发式，非深度学习 |
| 运动分析 | Farneback光流 | `cv2.calcOpticalFlowFarneback`，计算全局平均运动向量 |
| 关键帧 | 中间帧+偏移 | 每段取中间帧，支持手动帧号和偏移量 |

### 2.2 姿态提取 🕺 (VideoPoseExtractor)

**源码位置**: `nodes.py` → `VideoPoseExtractor`

**功能**: 从视频中逐帧提取人体姿态，输出 OpenPose 格式的姿态图序列，供 WanVideoAnimateEmbeds 使用。

#### 执行流程

```
输入视频路径
  │
  ├─ 1. 视频路径解析
  │     ├─ 优先使用连线传入的视频路径（来自运动分析节点）
  │     ├─ 如果视频文件="(从连线获取)"且路径为空 → 自动从input目录找最新视频
  │     └─ 回退到手动选择的视频文件名
  │
  ├─ 2. 帧采样
  │     → 如果总帧数 ≤ 目标帧数: 全部使用
  │     → 如果总帧数 > 目标帧数: 均匀采样
  │     → 目标帧数强制为 4k+1 格式 (如81, 85, 89)
  │
  ├─ 3. MediaPipe 姿态检测
  │     → mp.solutions.pose: 33个身体关键点
  │     → mp.solutions.hands: 2只手，每只21个关键点
  │     → mp.solutions.face_mesh: 468个面部关键点
  │
  ├─ 4. 坐标转换 (MediaPipe → OpenPose)
  │     → MediaPipe 33点 → OpenPose 19点 映射表
  │     → 计算推导点: 颈部=(左肩+右肩)/2, 髋部=(左髋+右髋)/2
  │     → 保留置信度作为第三个分量 (x, y, confidence)
  │
  ├─ 5. 时序平滑 (_smooth_kps_sequence)
  │     → 滑动窗口加权平均（默认窗口=5帧）
  │     → 权重 = 置信度，减少帧间抖动
  │
  ├─ 6. 帧数插值 (_interpolate_kps)
  │     → 如果检测帧数 < 目标帧数
  │     → 线性插值补齐到目标帧数
  │
  └─ 7. 绘制 OpenPose 姿态图
        → 黑色背景上绘制骨骼连线和关键点
        → 四肢颜色区分: 橙色=左半身, 蓝色=右半身
        → 输出 [目标帧数, H, W, 3] 的 IMAGE tensor
```

#### 关键技术细节

| 技术 | 实现 | 说明 |
|------|------|------|
| 姿态检测 | MediaPipe Pose/Hands/Face | model_complexity=2（最高精度） |
| 坐标转换 | MP→OpenPose 19点映射 | 兼容 ControlNet/OpenPose 标准格式 |
| 时序平滑 | 置信度加权滑动窗口 | 减少单帧检测噪声导致的抖动 |
| 帧数对齐 | 线性插值 | 确保输出帧数=目标帧数(4k+1) |

### 2.3 提示词控制 📝 (PromptControlNode)

**源码位置**: `nodes.py` → `PromptControlNode`

**功能**: 将自动生成的运动提示词与用户自定义前缀/后缀合并，支持4种合并模式。

#### 合并模式

| 模式 | 逻辑 | 示例 |
|------|------|------|
| 合并 | 前缀 + 自动 + 后缀 | "cinematic, panning left, 4k" |
| 替换 | 有自定义前缀则替换自动词 | "my custom prompt" |
| 前缀 | 自定义前缀 + 自动词 | "dramatic, panning left" |
| 后缀 | 自动词 + 自定义后缀 | "panning left, slow motion" |

多段提示词用 `|||` 分隔，每段独立合并。

---

### 2.4 关键帧预览 🖼 (KeyframePreviewNode)

**源码位置**: `nodes.py` → `KeyframePreviewNode`

**功能**: 透传关键帧图像和帧信息，在 ComfyUI 前端显示预览。本身不做计算，只是提供 `OUTPUT_NODE` 的 UI 展示入口。

---

### 2.5 模仿提示词 🎭 (MimicPromptGenerator)

**源码位置**: `nodes.py` → `MimicPromptGenerator`

**功能**: 根据运动提示词和人物描述，生成完整的正面/负面提示词对。

#### 逻辑

```
运动提示词 + 人物描述 + 风格关键词
  → 合并为正面提示词
  → 如果开启质量增强: 追加 "masterpiece, best quality, highly detailed..."

默认负面提示词:
  "low quality, worst quality, blurry, distorted, deformed, ugly,
   bad anatomy, bad hands, missing fingers, extra digits,
   watermark, text, logo, static, jittery"
  + 用户自定义负面词
```

## 三、引擎层节点详解

### 3.1 分段规划 🧠 (YunjiiSegmentPlanner)

**源码位置**: `engine/planner.py`

**功能**: 将分段信息解析为可执行的段落计划（JSON），决定每段的帧范围、参考图策略、生成参数。

#### 执行流程

```
分段信息 + 运动提示词
  │
  ├─ 1. 解析分段信息 (_parse_segment_info)
  │     → 三级回退解析:
  │       ① 帧号格式: "帧0-96" → (0, 96, 96)
  │       ② 秒数格式: "0.0s-3.2s" → 按FPS换算为帧号
  │       ③ JSON格式: [{"start":0,"end":96}] → 直接解析
  │
  ├─ 2. 解析提示词 (_parse_prompts)
  │     → 优先按 "|||" 分割
  │     → 回退按换行分割，去除 "镜头N:" 前缀
  │
  ├─ 3. 生成段落
  │     → 对每个场景:
  │       - 估算复杂度 (基于时长: <2s=0.8, <4s=0.5, >4s=0.3)
  │       - 自适应参数: 高复杂度→少帧多步, 低复杂度→多帧少步
  │       - 如果场景帧数 > (每段最大帧数 - 重叠帧数):
  │         自动拆分为多个子段
  │       - 每段记录: 起止帧、目标帧数、重叠量、参考图策略、提示词
  │
  └─ 4. 输出段落计划 JSON
        → SegmentPlan 数据结构:
          {
            "mode": "one_shot",
            "total_segments": 3,
            "resolution": [832, 480],
            "target_fps": 16,
            "segments": [
              {
                "index": 0,
                "start_frame": 0, "end_frame": 73,
                "target_frames": 74,
                "overlap_prev": 0, "overlap_next": 8,
                "ref_strategy": "user_image",
                "prompt": "...",
                "params": {"steps": 20, "cfg": 5.0, "denoise": 1.0, "width": 832, "height": 480}
              },
              ...
            ]
          }
```

#### 三种生成模式

| 模式 | 说明 | 参考图策略 | 拼接方式 |
|------|------|-----------|---------|
| one_shot (一镜到底) | 连续链式生成，每段用前段末帧作参考 | 第1段=用户参考图，后续=前段末帧 | 交叉淡化 |
| smart_split (智能分段) | 独立生成每段，转场处编排 | 自动选取 | 硬切/淡化 |
| sliding_window (滑动窗口) | 滑动窗口推进，适合超长视频 | 前段末帧 | 交叉淡化 |

#### 参考图策略

| 策略 | 说明 |
|------|------|
| `user_image` | 使用用户提供的参考图（第1段默认） |
| `prev_last_frame` | 使用前一段的最后一帧（一镜到底模式） |
| `auto_select` | 自动选择最佳参考图（智能分段模式） |

### 3.2 链式执行 ⛓ (YunjiiSegmentRunner)

**源码位置**: `engine/runner.py` + `engine/adapters/comfyui.py`

**功能**: 按照段落计划，逐段修改工作流参数，通过 ComfyUI HTTP API 提交生成任务，收集结果。

#### ⚠️ 核心原理与当前限制

**链式执行的设计思路是**：

```
段落计划中有3段
  → 修改工作流参数（提示词、帧数、参考图等）
  → 提交第1段到 ComfyUI 队列 → 等待完成 → 提取末帧
  → 用第1段末帧作为第2段参考图 → 提交第2段 → 等待完成 → 提取末帧
  → 用第2段末帧作为第3段参考图 → 提交第3段 → 等待完成
  → 收集所有段的视频路径
```

**但这里有一个关键问题 — 队列死锁**：

```
ComfyUI 是串行执行队列的:
  当前正在执行: Runner 节点（占用了执行线程）
      ↓ Runner 通过 HTTP API 提交子任务到 /prompt
      ↓ 子任务进入队列，排在当前任务后面
      ↓ Runner 调用 adapter.wait() 轮询等待子任务完成
      ↓ 子任务需要 Runner 释放执行线程才能开始
      ↓ Runner 在等子任务，子任务在等 Runner
      → 死锁！直到30分钟超时
```

**解决方案**：

| 方案 | 说明 | 状态 |
|------|------|------|
| A. 双实例模式 | 启动第二个 ComfyUI 实例（不同端口），Runner 连接到第二个实例 | 可用 |
| B. 直接调用模式 | Runner 不走 HTTP API，直接调用 ComfyUI 内部执行函数 | 待开发 |
| C. 异步队列模式 | Runner 提交后立即返回，子任务异步执行，通过回调收集结果 | 待开发 |

#### 执行流程详解

```
段落计划 JSON + 工作流模板 JSON
  │
  ├─ 1. 解析段落计划 (SegmentPlan.from_json)
  │
  ├─ 2. 发现工作流节点 (adapter.discover_nodes)
  │     → 扫描工作流JSON中的 class_type
  │     → 映射到角色: animate_embeds, sampler, text_encode, ref_image, video_combine
  │     → 验证必要节点是否存在
  │
  ├─ 3. 查询 ComfyUI 队列状态
  │     → GET /queue → 检查是否有任务在运行
  │
  ├─ 4. 逐段执行循环
  │     for seg in plan.segments:
  │       │
  │       ├─ 4a. 确定参考图
  │       │     → 第1段: 用户参考图
  │       │     → 后续段: 前段末帧 (one_shot模式)
  │       │
  │       ├─ 4b. 修改工作流 (adapter.modify_workflow_for_segment)
  │       │     → 深拷贝工作流JSON
  │       │     → 修改 AnimateEmbeds: width, height, frames
  │       │     → 修改 Sampler: steps, cfg
  │       │     → 修改 TextEncode: prompt, negative_prompt
  │       │     → 修改 LoadImage: 复制参考图到input目录并更新路径
  │       │
  │       ├─ 4c. 提交工作流 (adapter.submit)
  │       │     → POST /prompt → 获取 prompt_id
  │       │
  │       ├─ 4d. 等待完成 (adapter.wait)
  │       │     → 每2秒轮询 GET /history/{prompt_id}
  │       │     → 超时1800秒(30分钟)
  │       │     → 每15秒写入调试日志
  │       │
  │       ├─ 4e. 提取末帧 (_extract_last_frame)
  │       │     → cv2.VideoCapture 读取最后一帧
  │       │     → 保存到 output/yunjii_chain/seg_lastframe_时间戳.png
  │       │
  │       └─ 4f. 保存断点 (CheckpointManager)
  │             → output/yunjii_checkpoints/run_时间戳.json
  │             → 记录当前段号、末帧路径、已完成结果
  │             → 支持"续跑"模式从断点恢复
  │
  └─ 5. 输出执行结果 JSON
        → 每段的: segment_index, video_path, last_frame_path, status, duration_sec
```

#### ComfyUIAdapter 通信协议

| API端点 | 方法 | 用途 |
|---------|------|------|
| `/prompt` | POST | 提交工作流到队列 |
| `/history/{prompt_id}` | GET | 查询执行历史/状态 |
| `/queue` | GET | 查询队列状态 |
| `/interrupt` | POST | 中断当前执行 |

### 3.3 无缝拼接 🎞 (YunjiiSegmentStitcher)

**源码位置**: `engine/stitcher.py`

**功能**: 将多段视频拼接为一个完整视频，支持硬切和交叉淡化过渡。

#### 执行流程

```
执行结果 JSON
  │
  ├─ 1. 解析结果，筛选成功段
  │     → 只拼接 status=="success" 且视频文件存在的段
  │
  ├─ 2. 如果只有1段: 直接复制到输出，无需拼接
  │
  ├─ 3. 拼接模式选择
  │     ├─ hard_cut (硬切): 直接首尾相接
  │     ├─ cross_dissolve (交叉淡化): 段间N帧渐变过渡
  │     └─ auto (自动): 计算段间边界差异
  │       → 差异<30: 交叉淡化（内容连续）
  │       → 差异≥30: 硬切（内容跳变）
  │
  ├─ 4. 交叉淡化算法
  │     → 取前段末尾N帧 + 后段开头N帧
  │     → cv2.addWeighted 逐帧混合
  │     → alpha从0渐变到1: alpha = (j+1) / fade_frames
  │
  ├─ 5. 音频合并（可选）
  │     → 调用 ffmpeg 将原始视频音频添加到输出视频
  │     → -c:v copy (不重新编码视频)
  │     → -map 0:v:0 -map 1:a:0? -shortest
  │
  └─ 6. 输出
        → output/yunjii_v2v_时间戳.mp4
```

#### 边界差异计算

```python
# 取前段最后1帧 vs 后段第1帧
# 转灰度 → 计算像素绝对差均值
diff = np.mean(np.abs(last_gray - first_gray))
# diff < 30 → 内容连续，用交叉淡化
# diff ≥ 30 → 内容跳变，用硬切
```

## 五、WanVideo 生成管线

本插件的目标生成模型是 WanVideo，其标准管线如下：

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  T5 文本编码  │     │ CLIP视觉编码  │     │  姿态图输入   │
│  (umt5_xxl)  │     │ (xlm-roberta │     │ (OpenPose)   │
│              │     │  -large-vit   │     │              │
│ → text_emb   │     │  -huge-14)   │     │ → pose_emb   │
└──────┬───────┘     └──────┬───────┘     └──────┬───────┘
       │                    │                    │
       ▼                    ▼                    ▼
┌──────────────────────────────────────────────────────────┐
│              WanVideoAnimateEmbeds                        │
│                                                          │
│  整合 text_emb + clip_emb + pose_emb + 帧数/分辨率参数    │
│  → 输出 embeds (条件嵌入)                                 │
└──────────────────────┬───────────────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────────────┐
│                  WanVideoSampler                          │
│                                                          │
│  输入: embeds + model + steps + cfg                      │
│  过程: 从噪声开始，逐步去噪                               │
│  → 输出 latent (潜在表示)                                 │
└──────────────────────┬───────────────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────────────┐
│                    WanVideo VAE Decode                    │
│                                                          │
│  latent → 像素空间视频帧                                  │
│  → 输出 video frames (IMAGE tensor)                      │
└──────────────────────┬───────────────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────────────┐
│                  VHS_VideoCombine                         │
│                                                          │
│  视频帧 → 编码为 .mp4 文件                                │
│  → 输出视频文件                                           │
└──────────────────────────────────────────────────────────┘
```

### 模型要求

| 模型 | 文件 | 说明 |
|------|------|------|
| T5 文本编码器 | `umt5_xxl_fp16.safetensors` | 不支持fp8 scaled格式 |
| CLIP 视觉编码器 | `open-clip-xlm-roberta-large-vit-huge-14_visual_fp16.safetensors` | 必须是此特定模型 |
| WanVideo 主模型 | `wan2.1_i2v_480p_*.safetensors` | 图生视频模型 |
| VAE | WanVideo内置 | 无需额外下载 |

## 六、当前已知问题与限制

### 6.1 链式执行死锁（关键问题）

**问题**: Runner 在同一个 ComfyUI 实例中通过 HTTP API 提交子任务，由于 ComfyUI 串行执行队列，导致 Runner 和子任务互相等待。

**临时方案**: 启动第二个 ComfyUI 实例（不同端口），Runner 的 `ComfyUI地址` 参数指向第二个实例。

**计划方案**: 实现直接调用模式（B方案），Runner 不走 HTTP API，直接调用 ComfyUI 内部的执行函数。

### 6.2 人物检测精度

当前使用 Canny 边缘密度启发式检测，精度有限。未来可替换为轻量级人体检测模型（如 YOLOv8-nano）。

### 6.3 姿态提取速度

MediaPipe 逐帧检测较慢（约2-5fps），81帧视频约需16-40秒。未来可考虑批处理或GPU加速方案。
